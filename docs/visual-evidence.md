# Visual evidence for interval runs

Each interval evaluation writes one `report.html` and one
`visual-evidence.json` in the run directory. Open `report.html` in a browser.
Keep the report and its `evidence/` and `previews/` directories together.
The report needs no server, scripts, remote fonts, or network access.

To make the report again for a saved run, use Python:

```python
from viridian402.report import write_visual_report
write_visual_report("runs/REPLACE_WITH_RUN_ID")
```

The function checks the saved run with `load_run` first. It does not change
scores, predictions, accepted labels, or quality gates. The source image,
annotation, and truth must still be available at the saved paths. Their hashes
must agree with the saved snapshot. A missing or changed source causes a visible
render failure. The report does not fetch replacement data.

## Images and coordinates

The report reuses the evaluator's full-window preview. That image has its own
colour key and uses a reduced vertical scale. New issue crops use original
pixels with no resampling. Each issue has a plain source crop and a separate
overlay. Blue marks truth; orange marks prediction. Boundary lines use separate
left and right lanes so that coincident lines remain visible. Boxes use the
same colours. Open the PNG to inspect its native size; the HTML can reduce its
display size on a small screen.

Each issue records:

- Its category, explanation, severity, and number of affected rows.
- Truth and predicted boxes in full-image pixels. Either box can be null.
- Original boundary positions or labels, where applicable.
- The crop box, crop origin, and scale of 1. `crop = original - origin`.
- Boundary tolerance in pixels and the source image SHA-256.
- Source crop, overlay, and source legend crop paths, where available.

Boxes are `[left, top, right, bottom)` with exclusive right and bottom edges.
A boundary box is one pixel high. The crop has up to 24 pixels of context above
and below the affected range, clipped to the scoring window. The source legend
is saved once per case and referenced by each issue. A legend is optional when
the annotation has no legend box and the record has no legend swatch boxes.
If only swatch boxes are available, their union is used. If a declared legend
cannot render, evidence is incomplete.

## Issue selection

The report keeps the five largest issues per case. Severity is affected rows
divided by scoring window height. It sorts by severity, category, then box
coordinates for a repeatable result. The JSON also gives the total issue count.

- `missed_boundary`: truth has a boundary with no prediction. Affected rows span
  the adjacent truth boundaries or window edges.
- `false_boundary`: prediction has a boundary with no truth. Affected rows span
  the adjacent predicted boundaries or window edges.
- `shift_over_tolerance`: the nearest remaining truth and predicted boundaries
  form a diagnostic pair outside tolerance. Affected rows equal their distance.
- `wrong_lithology`: labels differ on a truth-filled segment. Affected rows equal
  that segment's height. A missing prediction has a null predicted box.

The report uses the scorer's interval clipping, label normalization, boundary
extraction, blank handling, and segment iterator. It follows the same greedy
distance and tie order for matches within tolerance. It checks those counts
against the saved score before it renders issues. Predictions within unlabelled
truth gaps do not create false boundary issues. Window endpoints are excluded.
Out-of-tolerance pairs explain shifts only. Both endpoints remain unmatched in
the score. Category counts are diagnostic and do not replace metric counts.
Different categories can cover the same rows.
The saved scorer hash must also agree with the current scorer. A different
scorer causes a visible render failure instead of a new interpretation.

## Failures and promotion claims

Every selected case remains in the report, including passes, crashes,
unlabelled cases, and render failures. Unlabelled accuracy is unavailable.
Model status and render status are separate. A missing preview, changed source,
failed required crop, or failed legend crop makes evidence incomplete. Thus a
run made with `--no-previews` has incomplete visual evidence, even if its issue
crops render. Existing previews remain unchanged.

`promotion_supported` is always false. The report does not approve promotion.
Missing required images block a promotion claim. Complete images alone do not
prove improved quality. Review paired metrics and data provenance separately.
The bundled demo cases are procedural fixtures; they are not real-data accuracy
evidence. No new data or labels are generated by this report.
